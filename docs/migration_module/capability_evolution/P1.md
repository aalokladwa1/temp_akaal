## 1. Summary of Capabilities Introduced in P1

- **P1.1 — Migration Spec & Physical Execution Contracts:** Immutable SHA-256 plan fingerprinting, fail-closed contract validation (H1/H5), and multi-custody governance gate enforcement (`GATE 2`).
- **P1.2/P1.2.1 — Production Migration Runtime:** `AkaalSuperEngine` orchestration facade, `ParallelReplicationScheduler`, `OraclePhysicalReader` → `PostgreSQLPhysicalWriter` parallel streaming data transport.
- **P1.3/P1.3.1 — Canonical Monitoring Contract:** Single aggregation authority via `MetricsRegistry` and `EngineGateway.get_monitoring_snapshot()`, with automatic primary key redaction over IPC.
- **P1.3.2 — Historical Monitoring & Restart Reconstruction:** Durably persisted run evidence in SQLite WAL (`artifacts/state.db`), supporting restart-safe historical run inspection (`LIVE` vs `HISTORICAL` modes).
- **P1.4/P1.4.1 — Enterprise Monitoring UI:** Dedicated 6-tab telemetry module (`<MonitoringModule />`) with migration isolation and dynamic migration listing (`get_all_migrations`).
- **P1.5 — Final Forensic Audit & Dual-UI Acceptance:** Comprehensive Mission Control audit, multi-database capability matrix, evolution record, and end-to-end real database verification.
- **P1.5D — Monitoring Home / Migration Run Explorer:** Portfolio-level landing screen (`<MonitoringHome />`) with canonical summary KPI cards, status filters (`All`, `Live`, `Paused`, `Completed`, `Failed`, `Terminated`), multi-engine display, and `LIVE` tag indicators while strictly preserving the frozen P1.4 detailed monitoring UI.
- **P1.6 — Universal Physical Transport Foundation:** Database-agnostic physical reader/writer contract architecture in `akaal/replication/contracts.py` with physical readers and writers for all four target engines (Oracle, PostgreSQL, MySQL, MSSQL) registered in `akaal/replication/resolver.py`.

## 2. Architectural Invariant: NO PAIR-SPECIFIC MIGRATION ENGINES

1. **Database-Agnostic Transport Pipeline:** AKAAL has exactly **ONE** physical transport runtime pipeline (`DataTransportStep` → `ParallelReplicationScheduler`). There are ZERO pair-specific migrator classes (such as `OracleToPostgresMigrator` or `MySQLToMSSQLMigrator`).
2. **Canonical Contract Resolution:** Connectors implement `IPhysicalReader` or `IPhysicalWriter` and register with `resolver.py`. Adding database #5 or database #50 requires only implementing the reader/writer contract and declaring capabilities — **ZERO** core engine modifications.
3. **Target Commit Precedes Checkpoint:** `writer.commit()` strictly precedes `checkpoint_store.mark_batch_committed()`. Target write failures trigger `writer.rollback()` and never advance the checkpoint.
